# Configuration

What the controller sends for each control, per preset and page, and its settings (SPEC §5,
§6.3). One description, [`config/schema.json`](../config/schema.json), gives everything else
(SPEC D-4):

| Generated by `tools/smcconf/gen.py` | For |
|---|---|
| `firmware/core/core_config.h` | the C structures the core runs on (`struct core_config`), their enums and flags |
| `firmware/config/cfg_schema.h` | the tables the firmware's codec checks values with (ranges, defaults, which field applies where) |
| [`config/smc-config.schema.json`](../config/smc-config.schema.json) | the JSON Schema of configuration files (FR-APP-21): completion and checks in editors |
| the field reference below | this document |

`gen.py --check` (part of `make -C firmware test`) fails when a generated file is not what the
description gives now. The current editor is JavaScript and reads this schema directly;
TypeScript type generation from D-4 is not implemented.

The description, file format and binary form are implemented in three codecs: the controller's
C, the Python tools and the editor's JavaScript. The controller carries the configuration
protocol ([link.md](link.md), "Configuration") and two-slot flash storage ("Storage" below);
`smcconf info`/`pull`/`push` and the editor use that protocol. Host tests, the editor against
`devhost`, and recorded physical-mixer runs are separate evidence: hardware results are in
[integration.md](integration.md) (the latest: "Hardware results, 2026-11-23").
What the editor and firmware share, and how both sides are checked together:
[app.md](app.md), "One product". The owner settled the format's open choices on 2026-11-08 (SPEC Q-19,
closed). Until the first public release a format change needs no migration: older files are
rewritten (FR-APP-22).

| Where | What |
|---|---|
| `config/schema.json` | the description: device counts, message types, kinds of controls, fields, settings, the binary form's records |
| `config/factory.json`, `config/test.json` | the firmware's built-in configurations as files (`core_config_factory()`, `core_config_test()`); a test checks that they are what the firmware encodes, byte for byte |
| `tools/smcconf/smcconf.py` | the command line (FR-APP-23): `validate`, `format`, `encode`, `decode`, `diff`, `size`; with the device: `info`, `pull`, `push`, `edit`, `save`, `revert`, `state`, `select`, `watch` |
| `tools/smcconf/devlink.py` | the configuration protocol's host side ([link.md](link.md), "Configuration") |
| `tools/smcconf/codec.py` | files ↔ the device's values ↔ the binary form, in Python (standard library only) |
| `firmware/config/cfgbin.c` | the device's codec: checks and decodes the binary form, writes it (C11, no allocation) |
| `app/editor/js/cfgbin.js` | the editor's codec: `codec.py`'s rules in JavaScript (the owner's choice, 2026-11-13; [integration.md](integration.md), I-5) |
| `firmware/store/cfgstore.c` | the configuration in flash: two slots, the header written last ("Storage") |
| `build/host/cfgtool` | the device's codec on the host (`firmware/sim/cfgtool.c`): `factory`/`test OUT`, `check FILE`, `batch` for the tests |

**Seeded three-codec checks** (2026-11-15): `tools/editortest/differential.py` reuses the
configuration tests' random valid models and damaged binary forms. C (`cfgtool`), Python and the
editor must agree on accepted/refused binaries and canonical bytes; the editor must encode the
same files and live-edit records, and C must apply those edits to the expected configuration.
A small fixed corpus runs with the editor tests in `make quick`/`make test` and `make linux`.
The harness is tested with planted C/editor disagreements; larger seeded runs are local, with
failure corpora retained under `build/differential/` ([integration.md](integration.md), T-1).
No format or runtime behavior changed.

## Files

A configuration file is JSON (UTF-8). Only `schemaVersion` is required; whatever is left out
takes its default, so a file can be as short as what it changes:

```json
{
  "schemaVersion": 1,
  "name": "Mono synth",
  "presets": [
    {
      "name": "Filter and envelopes",
      "channel": 3,
      "pages": [
        {
          "name": "Filter",
          "strips": [
            {
              "fader": {"name": "Cutoff", "type": "cc7", "number": 43},
              "encoder": {"name": "Resonance", "type": "cc7", "number": 44}
            }
          ]
        }
      ]
    }
  ]
}
```

- **Structure.** `presets` (up to the device's count), each with `pages` of `strips` (8: a
  `fader`, an `encoder` and the buttons `m`, `s`, `r`, `select`) and a `row` (the bottom row:
  `play`, `stop`, `rec`, `rew`, `ff`, `bankLeft`, `bankRight`, `up`, `down`, `left`, `right`).
  A missing item, or `null` in a list, is all defaults (sends nothing). A control is an object
  of its Normal layer's fields (below) plus `name` and `shift`.
- **Names** (`name` of the configuration, a preset, a page, a control, a control's own Shift
  layer; at most 64 characters)
  live only in the file (D-8): the device does not keep them. `id` (a UUID) and `revision`
  identify the configuration on the device (FR-APP-24).
- **Running revision (P-6).** The device assigns it when applying a full upload, each live
  edit command, a revert to saved or factory content, or a runtime setup. It increments the
  running unsigned 32-bit value, wrapping `4294967295` to `0`; uploaded revision values do not
  control it. The field in a file or binary remains valid metadata; a pull reports the running
  revision. Save (manual or automatic) writes that revision with the configuration but does not
  increment it. Revert replaces the running configuration without rewriting the saved slot;
  boot loads the saved revision unchanged, or starts the factory configuration at zero. The
  counter is therefore not a monotonic clock across reboots. A client-side edit with nothing
  to send, such as a change to names only, does not advance it.
- **Values** are names, not codes (`"type": "cc7"`, `"mode": "pickup"`); channels are 1–16.
- **Channels.** A preset has a `channel` (1–16, default 1). An assignment's `channel` is a
  number, fixed, or `"preset"`, the default: the channel of its preset, whatever that is at the
  time. Changing a preset's channel moves every assignment on `"preset"` and none of the fixed
  ones, so a whole preset follows a synth to another channel while a control that must reach
  another instrument stays where it is. The device stores both and resolves the channel when it
  sends (`core_channel()`); a file written by the tools has a `channel` only where it is fixed.
- **The canonical form** (`smcconf format`): defaults left out, keys in a fixed order, a control
  on one line. Two files with the same content format to the same text, so a diff in git shows
  only real changes; `smcconf format --check` tells a hook or CI whether a file is in it.

### A layer's fields

`type` decides which fields apply: `number` only for types with a number, `lo` and `hi` only for
types with a value range (not the relative encoder types), `start` only for encoders of such
types, `n` only for encoders in `div` or `step`, `noRelease` and `led` only for buttons. A field
that does not apply is an error, not ignored. A control with fields must have a `type` (type
`none` takes no other field). The tables in "Field reference" give the values and defaults;
`n` has none: in `div` and `step` it must be written.

### Encoders

An encoder of a type with a value range keeps that value (per target, FR-MOD-02) between `lo`
and `hi`; before anything has set it, it starts at `start`, by default the middle,
`(lo + hi + 1) / 2` rounded down (64 for 0–127, 8192 for 0–16383). Each click moves it by a
step its `mode` gives (FR-CTL-04). The fine step is 1 for a 7-bit target and the range / 2048 for a
14-bit one (7 on 0–16383; 1 with the global `fine14` = `lsb`):

| `mode` | Step per click |
|---|---|
| `acc0` | the fine step |
| `acc1`…`acc3` | the fine step, plus 1.5 for each acceleration level above the first that the mode's curve gives at this speed ([core.md](core.md), "Encoder acceleration"); `acc2` is the default |
| `fine` | the fine step, without acceleration |
| `div` | 1 every `n` clicks (1–127): slow, for values with few steps (a waveform switch) |
| `step` | `n` per click (1–127), without acceleration |

The first click of a turn is never accelerated, so a single click is always the fine step. The
global `encAccel` (50–200 %, default 100) scales the speed the acceleration sees. On relative types
(`relative2c`, `relativeBinOffset`, `relativeSignedBit`) the step of a 7-bit target is sent as it is.

### NRPN and RPN

`nrpn` and `rpn` are 14-bit types (FR-CTL-01): faders and encoders take both, buttons `nrpn`.
`number` is the parameter number as one value, 0–16383: MSB × 128 + LSB, the bytes that go out on
CC 99 and 98 (RPN: 101 and 100). So NRPN MSB 3, LSB 10 is `"number": 394`, and RPN 0 (pitch bend
sensitivity) is `"number": 0`. `lo` and `hi` are 0–16383 like the other 14-bit types, and the value
goes out on CC 6 (MSB) and 38 (LSB):

```json
"fader": {"type": "nrpn", "number": 394}
```

How the messages are framed, and what the core does with NRPN and RPN it receives:
[core.md](core.md), "NRPN and RPN". A preset's `paramNull` (`off`, the default, or `gesture`) ends
each gesture that sent NRPN or RPN with the null parameter (RPN 127/127). The 7-bit form (the MSB
alone, FR-CTL-01) is not a type yet.

### The Shift layer

`shift` says what the control does while Shift is active (FR-SH-01…04):

| `shift` | Meaning |
|---|---|
| absent | the kind's default: faders and buttons inherit the Normal layer; an encoder with a type gets its Normal layer in mode `fine` (FR-CTL-04) |
| `"inherit"` | the Normal layer |
| `"block"` | nothing |
| an object | a layer of its own, written in full |

An object is a complete assignment like the Normal layer: `type` is required and nothing comes
from the Normal layer, so what it does not write takes its default, not the Normal layer's value.
It can send anything the control's kind can, on any channel, in any mode:

```json
"encoder": {"type": "cc7", "number": 74, "shift": {"type": "cc7", "number": 71, "mode": "acc0"}}
```

turns CC 74 with acceleration and, under Shift, CC 71 without.

A layer of its own may have a `name` of its own, since it does something else (the owner,
2026-11-24): `"shift": {"name": "Resonance", "type": "cc7", "number": 71}`. Like every name it
lives only in the file and the editor (D-8): the binary form is the same with or without it, and a
configuration loaded from the mixer has none. Only a layer of its own takes one (the editor shows
its message while it has none); under `"inherit"`, `"block"` or the default the control's `name`
is shown.

Rules:

- to send nothing under Shift, write `"block"`: an object of type `none` is an error;
- the encoder's default Shift layer is the same target in `fine`: same type, channel, number,
  `lo`, `hi`, `start`, so the two layers move one value (FR-MOD-02); the tools leave it out of a
  file and write any other Shift layer in full;
- the navigation buttons of the row (`rew`, `ff`, `bankLeft`, `bankRight`, `up`, `down`, `left`,
  `right`) have no `shift`: with Shift they switch pages and presets, which is the firmware's
  (FR-SH-02).

The core sees two complete assignments per control.

### Errors

Every fault names its place and what is wrong, for example:

```
presets[0].pages[0].strips[3].encoder.number: 40 is outside 0-31
presets[0].pages[1].strips[0].encoder.n: needed in mode div
presets[1].row.rew.shift: the Shift layer of a navigation button is the firmware's (FR-SH-02)
presets[0].pages[2].strips[0].fader.shift: a layer of its own is written in full: its type at least
```

The JSON Schema catches them while editing; the schema never refuses a file the tools accept (a
test checks that on hundreds of altered files).

## Binary form

What the device stores and the configuration protocol carries ([link.md](link.md), "Configuration"): the device's values (channels
0–15, enums as numbers), no names, little-endian. Only what differs from a default is written, so
a configuration that changes little is small.

Header, 36 bytes:

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `SMCF` |
| 4 | 1 | binary version, 1 |
| 5 | 1 | header size, 36; a larger one is read (the rest skipped), for later versions |
| 6 | 2 | reserved, 0 |
| 8 | 4 | length of the records after the header |
| 12 | 4 | CRC-32 (as zlib's) of everything from offset 16 to the end |
| 16 | 4 | revision |
| 20 | 16 | ID (UUID; zeros: none) |

Then records, each `tag` (1 byte), `length` (1 byte), payload. A field mask says which fields
follow, in the order of the "Field reference" tables (bit 0 the first). A field not in the mask
takes its default; in a Shift layer, the Normal layer's value (the binary form stores a Shift
layer as a difference to keep it small; files write it in full).

| Tag | Record | Payload |
|---|---|---|
| 1 | global | mask (1 byte), then `layerMode` 1, `pickup` 1, `gestureMs` 2, `hybridMs` 2, `encAccel` 1, `fine14` 1, `save` 1 |
| 2 | preset | preset (0-based) 1, mask 1, then `channel` 1 (0–15), `shiftMode` 1, `noteOff` 1, `paramNull` 1 |
| 3 | Normal layer | page 1, control 1, mask 2, then `type` 1, `channel` 1 (0–15; 16 the preset's), `number` 2, `mode` 1, `n` 1, flags 1, `lo` 2, `hi` 2, `start` 2 |
| 4 | Shift layer | page 1, control 1, kind 1 (0 inherit, 1 own assignment, 2 block); for an own assignment: mask 2 and the fields that differ from the Normal layer |
| 0x81 | the LED light (optional) | mask (1 byte), then `ledLevel` 1, `ledUnlit` 1 |

- **Controls**: page 0–3 and control `group × 8 + strip` (groups 0 fader, 1 encoder, 2 M, 3 S,
  4 R, 5 SELECT); the bottom row is page 255, control 0–10 in the order of `row`. Flags: bit 0
  `noRelease`, bits 1–2 `led` (0 value, 2 off, 4 on).
- **The global settings' records**: the global record's mask is one byte, so the settings after
  its first eight go into a record of their own. The LED light's (`ledLevel`, `ledUnlit`; SPEC
  §5.7, 2026-11-25) is tag 0x81, optional: a firmware before it skips it and plays the rest. The
  schema says which record a global setting belongs to (`"record": "global2"`); `schema.py`'s
  `global_records` and `cfg_schema.h`'s `cfg_global_tag` / `cfg_global_first` list them in order,
  and the field numbers in errors count over all global settings.
- **Order**: a Normal or Shift layer belongs to the preset record before it; each record at most
  once (one global record, one LED light record, one per preset, one Normal and one Shift layer
  per control); a Shift
  layer comes right after its control's Normal layer, or alone. A control without a Normal layer
  sends nothing; one without a Shift layer gets its kind's default (above).
- **Later versions**: an unknown record with tag bit 7 set is skipped (optional data); any other
  unknown record, field mask bit or out-of-range value refuses the whole configuration.
- **Canonical form**: what all three codecs write: the global record if a setting differs, then
  the LED light's if one of its settings differs; per preset
  in order, its record (if it has a setting or a control), then its controls page by page, group
  by group, strip by strip, then the row, each with a Normal layer if its type is not `none` and
  a Shift layer if it is not the default. Other orders and masks that are read correctly are
  accepted too; `cfgtool check` says whether a form is canonical.

The device checks everything before the core can see it: `cfgbin_decode()` with no destination
only checks (for an upload, before it is stored), with one it also fills `struct core_config`. A
refusal is logged (`cfg` module, WARN) with its reason, byte offset, preset, page, control and
field.

### Edits

A live edit (CFG_SET, P-1; [link.md](link.md), "Configuration") carries records of this form for
one preset, with no header: at most one global record and one LED light record, at most that
preset's record, and Normal
and Shift layers of that preset's controls, at most 184 bytes. Their meaning differs from a whole
configuration's in one way: what a record names is replaced whole, the rest stays.

- A global or preset record replaces all of its settings: a field not in its mask takes its
  default (mask 0: every setting back to its default).
- A control named by a Normal or a Shift record is replaced whole: with no Normal record it sends
  nothing, with no Shift record it gets its kind's default Shift layer. A control with neither is
  written as an empty Normal layer (`3 4 page control 0 0`: mask 0, type `none`).
- A preset record must name the edit's preset (else `where`).

`cfgbin_patch()` (C) checks such records (no destination) and applies them to a configuration;
`codec.edits(old, new)` (Python) and `Codec.edits(old, new)` (the editor) make the list of
`(preset, records)` that turns one configuration into another: every setting record or control
that differs, written whole in the canonical form, the global settings' records first (each one
that differs) with the first preset that changes (or preset 0), packed in order into edits of at
most 184 bytes; names do not count
(none when only names differ). The three agree byte for byte (below).

## Versions and migrations

Until the first public release a format change rewrites `config/*.json` and the tests, and the
schema's version stays 1 (FR-APP-22; the owner, 2026-11-13, Q-29: the global field `save` came in
so). From the release on, an update of the firmware or of the editor must not lose a user's
configuration, so the formats are kept ready for migrations now.

What exists today:

- every format names its version: the file's `schemaVersion`, the binary form's version (header
  byte 4) and its header size (a larger header is read, the rest skipped), the configuration
  protocol's version (CFG_INFO); GET_INFO gives the firmware's build;
- the binary form skips an unknown record whose tag has bit 7 set (optional data), and refuses
  any other unknown record, mask bit or value, so an old firmware never plays a configuration it
  half understands;
- the editor and `smcconf` refuse a mixer whose protocol, binary form or schema they do not know,
  and say which side to update (FR-CFG-07); a file or binary form from a newer release says "made
  by a newer version of better-smc-mixer … update the editor" (or "the tool"), in the same words in
  `codec.py` (`version_text`) and the editor (`versionText` in `js/schema.js`), tested on both sides;
- every version is written in several places (C headers, the editor, the Python tools, the
  transcript): `tools/release/check_versions.py` in `make quick` reads the schema's, the binary
  form's, the configuration protocol's, the link's and the log format's from 20 places and fails on
  one that differs from its source (`config/schema.json`, `cfglink.h`, `link.h`, `smclog.h`).

The migration code itself (a dispatch on the version, one step per version) is not written yet:
with one version of each format there is nothing to migrate and nothing to test it on, and
FR-APP-22 rewrites the files until the release. It comes with the first format change after the
release, in all three codecs at once.

What the release needs (planned, not built):

1. **Files**: the editor and `smcconf` read every older `schemaVersion` and migrate it step by
   step (one function per version), then write the current one; a newer file is refused with
   "update the editor".
2. **The configuration saved in the mixer** across a firmware update: the firmware reads the
   binary versions it knows (its own and the ones before it, migrated on load); one it does not
   know (after a rollback) starts the factory configuration and leaves the slot as it is until the
   next save, so going forward again finds it. A slot already holds the whole binary form, whose
   header names its version.
3. **An editor and a firmware of different versions**: the editor keeps speaking the older
   protocol versions it knows (sending the binary form the mixer reads), and refuses only what it
   cannot; the release manifest names the oldest editor a firmware needs ([app.md](app.md),
   "Hosting on GitHub Pages").
4. **Adding a field** after the release is a new binary version or a new optional record, so an
   older firmware is never sent a mask bit it refuses. The LED light (0.1.2) was the first: an optional
   record (0x81), so 0.1.0 and 0.1.1 skip it, play the rest and keep their LEDs at full light. A
   configuration they save and send back has no light record, which reads as the defaults: the
   editor then shows full and dark, which is what that firmware shows. Their editor and
   `smcconf` (`schemaVersion` 1 too) refuse a file that sets the light, with "unknown keys": a
   file of 0.1.2 with the light at its defaults reads in both.

## The three codecs agree

The Python tools, the firmware and the editor implement the same rules three times; the tests make
them the same (`make -C firmware test`):

- `test_cfgbin` (C): CRC, round trips of the built-in configurations, the largest configuration,
  every error code on hand-built records, header faults, and 20 000 random damaged forms with a
  correct CRC: checking and decoding agree, and whatever is accepted re-encodes to a form that
  decodes the same.
- `tools/smcconf/test_smcconf.py`: the built-in configurations are `config/*.json` byte for
  byte; on 500 damaged forms (records removed, repeated, swapped, cut, altered; header faults;
  unknown records) and on random configurations, `cfgtool` and the Python codec accept and refuse
  the same ones and write the same bytes; file round trips; the Shift rules and errors; the JSON
  Schema against the example files, random files and known faults; the command line. The random
  cases use a fixed seed (`SMCCONF_SEED` sets another).
- `tools/editortest/run.mjs` with `vectors/binary.json` (written by `vectors.py` from `codec.py`):
  the editor's codec writes the four built-in and generated configurations, with and without an ID
  and a revision, and the factory one with the LED light set, byte for byte as `codec.py`, reads
  them back to the same file (names aside),
  refuses the broken forms (six of the whole file, six of the LED light's record), skips an
  unknown optional record, and refuses every file of
  `faults.json`.
- Edits: `test_cfgbin` (`test_patch`: every control of the factory configuration patched into the
  test one gives the factory's controls; refusals), `test_smcconf.py` (`EditTest`: on random pairs
  of configurations `codec.edits()` applied by `cfgtool patch` gives the new configuration), and
  `run.mjs` with `vectors/edits.json` (27 cases: the built-in and generated configurations into
  each other, small changes and their undoing, the LED light among them, names only): the editor
  makes the same edits as
  `codec.py`, byte for byte.

## Sizes (SPEC Q-3)

| | Binary form |
|---|---|
| the factory configuration (4 presets × 4 pages) | 7 363 bytes: 36 header, 1 831–1 832 per preset |
| the test configuration | 8 556 bytes |
| every field of every control set, with a Shift layer each | 26 584 bytes (6.6 KB per preset) |
| the bound the code uses (`CFGBIN_MAX`) | 30 128 bytes |

`number` takes 2 bytes since NRPN and RPN (2026-11-11): an NRPN parameter number is 14-bit. That
added about 0.8 KB to the factory configuration's binary form and 2 bytes to each assignment in
RAM.

In RAM the decoded configuration is `struct core_config`, 24 388 bytes (6.1 KB per preset, 1.4 KB
per page; an assignment is 14 bytes), and the decoder needs about 480 bytes of stack (476 in the controller's build, 2026-11-11; it runs on
the control task's 3 KB); the codec is 5 KB of code (`-Oz`,
`tools/env/check_device.sh`). So flash is not what limits the number of presets and pages: the
two slots of 32 KB ("Storage") take 64 KB of the 488 KB available, and the largest form
possible is 30 KB (`CFGBIN_MAX`). RAM is: each more
preset of 4 pages costs 6.1 KB of a heap of 38 KB left (37 984 bytes in the controller's build of 2026-11-11, with
the protocol's 16 KB buffer; `build_app.sh` prints it),
unless only the active preset is kept decoded.

## Storage

SPEC FR-CFG-04, NFR-05; the owner's choice of 2026-11-11 (Q-22): two slots of our own. Since
Q-26 (2026-11-13), saving is manual by default (CFG_SAVE); `global.save = auto` enables saving
after a quiet pause. Code: `firmware/store/cfgstore.c`
(portable, the slots), `firmware/link/cfglink.c` (when to save, the load at start; [link.md](link.md),
"Configuration", "Autosave"), `firmware/platform/br25/flash_br25.c` (the SDK's flash driver).

- **Where.** Two slots of 32 KB at flash `0x25000` (A) and `0x2D000` (B), below our application
  area (`CFGSTORE_FLASH_AT`; `tools/image/installplan.py`'s `CFG_AT`, a test checks the two agree),
  in a part of the stock VM's range unused in the pre-install dumps (only sector `0x24000`
  held its records). That is observed use, not a permanent stock allocation guarantee: SincoOTA
  V012 → V013 erased this range on 2026-11-14 ([app.md](app.md), "After an M-Vave update"). Moved there on
  2026-11-12 (SPEC Q-23, the owner): with the BLE stack
  `app.bin` needs the room above the area ([ble.md](ble.md), "Flash"). Our VM now runs from the
  area's end up to the stock update loader at `0x6E000`. From 2026-11-11 to 2026-11-12 the slots were
  at `0x5E000..0x6DFFF`, the top of what is our VM again; a configuration saved there is not read
  any more (push it again after installing).
- **A slot** is a 32-byte header and the binary form after it: magic `SMCS`, version 1,
  generation u32, length u32, the form's CRC-32 u32, and the header's own CRC-32 over the 28
  bytes before it. A slot takes up to 32 736 bytes, more than the largest form (`CFGBIN_MAX`).
- **A save** writes the slot that does not hold the newest configuration: it erases the sectors
  the form needs (4 KB each; a factory configuration needs 2), programs the form a page (256 bytes)
  at a time and reads each page back, then programs the header, with a generation one above the
  newest, and reads the header and the whole form back. The header is the commit mark: until it
  is down, the slot has no valid header and the other slot is untouched. So a power cut at any
  moment leaves the newest complete configuration readable (`test_cfgstore.c` cuts the power
  before every flash operation of a save, the operation it hits half done: every start after it
  loads the old configuration byte for byte, or the new one when the cut came after its header).
- **At start** the firmware takes the slot with the highest generation whose header and form
  check and that `cfgbin_decode()` takes, else the other one, else none: the factory
  configuration. A form longer than the transfer buffer (16 KB) is passed over. CFG_INFO's source
  says `stored`, with the stored ID and revision.
- **When.** Only configurations received/edited over the protocol are saved, never a CORE_SETUP.
  Manual Save starts without the initial quiet pause; autosave waits 3 s after the last transfer
  command and touch of a control. Both run one step per USB-task round (an erase, or up to four
  pages) and pause between steps while the panel is in use ([link.md](link.md), "Autosave").
  About 2 erases and 10 steps for a factory configuration. A successful CFG_SAVE reply means
  accepted, not completed: wait for clean storage. The editor does so: it shows Saved, and
  Update's Save first goes on, only after the acknowledgement and clean storage (R07).
- **Wear.** One save erases one slot's sectors, alternately A and B. At 100 000 erase cycles per
  sector (a usual NOR rating, ⚠️ the chip's own rating is not known) that is 200 000 saves.

### The panel's state

The owner's decision of 2026-11-12 (SPEC Q-25): after a power-off Bluetooth is on or off, and the
preset and the page are selected, as they were left. Code: `firmware/store/statestore.c`
(portable, the records), `ctl_state()` and `ctl_restore_state()` (`firmware/ctl/ctl.c`), the save
in `cfglink_poll()` ([link.md](link.md), "Autosave"); host tests `test_statestore.c` (power cuts),
`test_ctl.c` and `test_cfglink.c` (`test_state`).

- **What.** One 32-bit word: bits 0-1 Bluetooth (0 off, 1 on, 2 none in this build), 2-3 the
  preset, 4-5 the page, 8-15 each preset's last page (2 bits each), so a preset switch after a
  start lands where it did before. A received configuration restarts the core on preset 1 page 1
  (as before), and that is then the state kept.
- **Where.** Two sectors of 4 KB right after the slots, `0x35000` and `0x36000`
  (`STATESTORE_FLASH_AT`), in the same observed-free part of the stock VM's range. The storage
  operations in `flash_br25.c` reach `0x25000..0x36FFF` only (boot selection has separate
  operations); `installplan.py` plans around it (its rollback R2 erases
  it with the slots); an installation leaves it.
- **A record** is 16 bytes: `SS`, version 1, 0, a sequence number u32, the word u32, the CRC-32 of
  the 12 bytes before it. A save programs the next erased record of the sector holding the newest
  one and reads it back: one 16-byte program, no erase. When that sector is full (256 records) the
  save erases the other one and starts it; the full one stays as it was until the new record is
  down, so a power cut at any moment leaves the newest complete record (the test cuts before every
  operation). One erase per 256 saves, the sectors in turn: at 100 000 cycles per sector, about 51
  million saves.
- **At start** the newest valid record in either sector is restored after the configuration is
  loaded: Bluetooth (with `BLE=1`; the stack then advertises or not from the start), each preset's
  last page, the preset and the page (log: "state loaded", engine "state restored: …"). With
  nothing saved (erased state sectors): Bluetooth on, preset 1 page 1. A reinstall normally keeps
  those sectors, so it does not imply this default. Records that are
  neither valid nor erased are passed over; the next save goes after them.
- **When.** Once the state differs from the one in flash and no control has been touched for 3 s
  (the BT long press and the preset/page buttons are touches), from the USB task, never while a
  configuration is being saved. A failed write is tried three times, then not again until the
  state changes (log ERROR "state: writing the record … failed"). A power-off within 3 s of the
  last change loses that change.
- ✅ On the mixer, 2026-11-13 (controller 29, build 727aacbc, `BLE=1`; session
  `logs/sessions/2026-11-13-app29-state-restore`): after the install "state: none saved", Bluetooth
  on, preset 1 page 1. Injected Shift + « (preset 3), Shift + ▼ (page 2) and a BT long press:
  "state saved: 00001018 (record 1, flash sector 0)" 3 s after the last press, once. After a soft
  restart: "state loaded: 00001018", "state restored: bluetooth off, preset 3 page 2", and the stack
  came up without advertising ("bluetooth off: no advertising"). Back to preset 1 page 1 and
  Bluetooth on: record 2, and the vendor's adapter connected again by itself. ✅ A power-off by
  hand (the owner, the same day): Bluetooth, the preset and the page came back as left. ✅ The scan
  during a save (session `logs/sessions/2026-11-13-app29-state-save-gaps`, five saves 10 s apart,
  the panel quiet): one gap per save, 9.8–9.9 ms (195–197 periods of 50 µs), all in `smc_usb` at
  the return of the SDK's `_norflash_write`, which is a plain page program (command 0x02, no
  erase; the listing): the SDK holds the scan off about 10 ms for any flash command, a program as

✅ Ran on the mixer on 2026-11-12 (controller 20, build `9919619d`; "The first run" below), the

- **The SDK's flash driver** (`cpu.a`, as our own build's listing shows its VM using it):
  `sfc_erase(2, addr)` erases 4 KB ✅ (from the listing: the VM's `_vm_area_erase` steps by 4096
  with command 2; a third-party port in the SDK calls command 2 "64k" in a comment, which the code
  does not bear out). `sfc_write()` returns the length whatever happened (it refuses past the
  flash's end or where `sdfile_check_write_protect()` says no), so every program is read back.
  `sfc_read()` reads below a boundary the driver keeps raw and XORs the buffer with the ENC
  keystream of `0xFFFF`, above it through the cache's mapping. The boundary is our area's start,
  `0x41000` (inferred; the firmware cannot read it: the SDK keeps it to `cpu.a`), so since the slots
  moved below it `flash_br25.c` XORs the same keystream again after each read (the transform is
  its own inverse; ✅ the listing, and ✅ the run of 2026-11-12, "At the new place" below: the
  slots below `0x41000` read back as written). Were it wrong, every save would fail its read back

  restricts these storage operations to the configuration slots and the panel-state sectors;

- **A panel that is never quiet.** Every fader event counts as a touch, so a fader that reports

## Command line

```
python3 -I tools/smcconf/smcconf.py validate FILE...        # JSON or binary; exit 1 if any is not valid
python3 -I tools/smcconf/smcconf.py format FILE [-o OUT | --in-place | --check]
python3 -I tools/smcconf/smcconf.py encode FILE -o OUT.bin  # byte for byte what the firmware writes
python3 -I tools/smcconf/smcconf.py decode FILE.bin [-o OUT.json]
python3 -I tools/smcconf/smcconf.py diff A B                 # a line per field that differs; exit 1 if any
python3 -I tools/smcconf/smcconf.py size FILE                # bytes in all and per preset
python3 -I tools/smcconf/smcconf.py info --port PORT         # the device's versions, limits, running ID and revision
python3 -I tools/smcconf/smcconf.py pull --port PORT [-o OUT.json | --binary -o OUT.bin]
python3 -I tools/smcconf/smcconf.py push FILE --port PORT [--no-verify] [--save | --wait-save]
python3 -I tools/smcconf/smcconf.py edit FILE --port PORT [--save]   # only what differs, live (CFG_SET)
python3 -I tools/smcconf/smcconf.py save --port PORT         # what the device plays becomes what it starts with
python3 -I tools/smcconf/smcconf.py revert --port PORT       # the device plays what it starts with again
```

`pull`, `push`, `edit`, `save` and `revert` talk to the device's command link (PORT: its USB CDC
port, such as `/dev/cu.usbmodem…`, or `--midi NAME` for SysEx over a MIDI port; [link.md](link.md),
"Configuration"):

- `pull` writes the running configuration as canonical JSON, without names (the device does not
  keep them, D-8; FR-APP-24's matching by ID is the editor's), or its binary form.
- `push` checks FILE (JSON or binary) here first, refuses a device whose protocol, binary or
  schema version is not the tool's (FR-CFG-07) or that takes fewer bytes, sends it, waits until
  the device has applied it, checks its ID, then compares the read-back with the sent content
  and the revision the device reported. `--no-verify` skips the read-back.
  The device checks it again in full before the core sees it; a refusal names cfgbin's error and
  where (byte, preset, page, control, field).
- `edit` pulls the running configuration, sends what differs from FILE as live edits
  ("Edits"; the device keeps playing, its page, Shift and values stay), then reads it back and
  compares; the ID stays the device's, and the tool reports the read-back revision.
- Saving follows the configuration's global setting `save` (Q-26): `manual` (the default) keeps
  what the device plays unsaved (storage `unsaved`) until `save` or `--save`, which save and
  wait; `auto` saves by itself, 3 s after the last change and the last touch of a control
  ("Storage"), and `--wait-save` waits for that (up to 30 s; it fails on `unsaved`: use
  `--save`). `info` shows the storage's state and the saved generation.
- Exit 1: refused, no reply after 3 tries (`--timeout` seconds each), or a mismatch.

`diff` compares what the device would do (every field, defaults filled in) and the names, so two
files that write the same configuration differently are the same.
